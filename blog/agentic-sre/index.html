Agentic SRE: Seeing What’s Going On (and Fixing It Faster)

01 · Foundations

Why Agentic SRE — and What It Means in Practice

Modern data and cloud estates rarely live inside a single observability pane. A single business workflow often spans dbt transformations, GCP log-based metrics and BigQuery slots, Azure pipelines and services, Grafana boards, and Datadog APM. When something breaks—or silently stalls—platform teams find themselves wrestling with four recurring questions:

  • Where are we flying blind today? (Systems without clear owners, missing lineage signals, or silent job stalls that users discover before monitoring does.)
  • Which alerts are genuinely useful, and which are noise? (Ten downstream symptoms paging three channels for a single upstream delay.)
  • What repetitive operational toil can we safely automate? (Manual retries on transient network resets, warehouse contention, or late upstream feeds.)
  • Where does AI meaningfully help—and where does deterministic code belong instead?

Agentic SRE applies bounded AI agents to Site Reliability Engineering across triage, cross-system investigation, communication, and governed remediation. Crucially, the agent does not replace monitoring tools or on-call engineers. Instead, it sits between signals and people to shrink the time and cognitive load required to move from alert → understood → resolved.

Architectural Stance: Signals, Not Firehose Configure logging and detection conservatively inside each native observability tool (Datadog, Grafana, GCP, Azure Monitor, dbt Cloud). Send only alerts, notifications, and summarized signals to the agent—never stream raw log firehoses into an LLM context window. Existing tools detect; the agent correlates and reasons.

Rather than granting open-ended shell access, scoping an Agentic SRE system starts by bounding the exact four operational decisions the agent is allowed to make:

  1. Escalate an ongoing event with correlated context, blast radius, and cited evidence.
  2. Escalate a predicted future failure or SLA breach before consumers feel the impact.
  3. Watch an ambiguous situation more carefully via timed rechecks and explicit exit rules.
  4. Trigger bounded retries or failure recovery strictly through allowlisted, idempotent runbooks.

The Core Loop: Observe → Orient → Decide → Act → Learn

Five Non-Negotiable Engineering Principles

  • Signals, not firehose: Native monitoring tools detect anomalies cheaply; the agent reasons over structured events and targeted read-only lookups.
  • Deterministic first, AI second: Use explicit rules for known patterns, routing, and risk caps; reserve the LLM for cross-tool correlation, ambiguity, and plain-language synthesis.
  • Graduated autonomy: Authority is earned per action type through historical replay evidence—never granted globally.
  • Humans own outcomes: Every agent action must be explainable, auditable, and reversible—or else it is escalated to a human.
  • Fail safe: If the agent, LLM provider, or intake queue is down or uncertain, critical alerts still reach on-call humans over an independent bypass path.
02 · Topologies & Autonomy

Agent Architecture Patterns & Earned Autonomy (L0–L4)

Mature reliability setups rarely jump straight to a complex multi-agent mesh on day one. Four patterns form a natural progression—and complement one another in production:

Pattern How It Works Strengths Trade-Offs Adoption Role
A. Rules + LLM Assistant Deterministic engine routes & deduplicates; LLM summarizes context and recommends next steps. Simple, predictable, low cost & low latency Limited multi-hop investigation across tools START HERE
B. Single Tool-Using Agent One agent reasons step-by-step calling read-only tools (run history, dashboards, lineage). Flexible multi-signal investigation Harder to regression-test; wider prompt-injection surface PHASE 2
C. Supervisor + Specialist Agents Coordinator delegates to Triage, Investigation, Prediction, Remediation, and Comms specialists. Separation of duties; narrow per-agent permissions More moving parts & orchestration telemetry TARGET STATE
D. Vendor-Embedded Agents Built-in AI assistants inside Datadog, Grafana, GCP, or Azure. Zero build effort; fast per-tool triage Siloed within one vendor; blind to cross-system lineage COMPLEMENT

Target State: Supervisor + Specialists Behind a Non-AI Policy Engine

The single most important security boundary in the target architecture is simple: the agent that reasons never holds production write credentials. Specialists investigate using read-only tools (exposed cleanly via MCP with per-tool scopes) and emit a structured action proposal. A deterministic, non-AI policy engine validates allowlists, blast radius, rate limits, and approval tokens before an isolated executor runs anything.

Graduated Autonomy Levels (L0 to L4)

Autonomy is assigned per action type, not per system. A transient, idempotent job retry might earn L3 after 30 clean shadow evaluations, while a partition backfill remains permanently at L1 or L2:

Level Mode Agent Responsibility Human Responsibility Concrete Example
L0 Observe Reads events & logs recommendations privately Handles incident normally (compares offline) Shadow-mode pilot evaluation
L1 Advise Enriches alert, posts root-cause summary & runbook link Decides and executes remediation Slack/Teams brief with lineage & recent commits
L2 Propose Prepares exact parameterized action + rollback plan Approves or rejects with one click “Retry dbt job X from failure point? [Approve / Reject]”
L3 Act & Notify Executes allowlisted low-risk action, verifies, then notifies Reviews audit trail; can halt or undo Auto-retry a transient upstream 503 timeout once
L4 Autonomous Handles incident class end-to-end Audits periodically Not recommended for initial enterprise rollouts

Four supporting capabilities make graduated autonomy trustworthy: RAG over runbooks, postmortems, and lineage so claims carry citations; read-only MCP tool servers for run history, dashboards, and deploy logs; incident memory so the agent tracks active watches and never contradicts prior steps; and an offline replay evaluation harness to benchmark historical alerts before promoting any action up the L-ladder.

03 · Pillar 1 — Observability Foundation

Seeing What’s Happening: Closing Blind Spots Before Adding AI

An agent cannot reason over telemetry that does not exist. Before wiring LLM workflows, reliability teams need honest answers to where they are flying blind across multi-cloud pipelines and application services.

  • Build a system coverage map first: Document every critical service and pipeline alongside its owner, tier, upstream/downstream dependencies, active monitoring tool, signals covered, and explicit blind spots (especially across secondary cloud footprints like Azure or partner feeds).
  • Cover all five data-observability pillars: Green job exit codes routinely mask bad data. Instrument freshness, volume, schema changes, distribution/quality (e.g., dbt test assertions), and lineage.
  • Add dead-man’s-switch heartbeats: Alert when an expected batch, stream checkpoint, or metric fails to arrive. Silence is not health.
  • Propagate correlation IDs end-to-end: Pass run_id, pipeline_id, and OpenTelemetry trace_id across orchestrators and services so the agent links causal chains deterministically rather than guessing by timestamp.
  • Monitor the monitors: The event intake queue, the reasoning agent, and the runbook executor require their own liveness heartbeats.
04 · Pillar 2 — Signal Quality

Getting Useful Alerts: Canonical Contracts & SLO Burn Rates

Alert fatigue kills on-call effectiveness long before an LLM enters the picture. Every alert that wakes or interrupts an engineer must be actionable; otherwise it belongs in an asynchronous ticket, a daily digest, or the trash.

The Canonical Alert / Event Contract

Normalizing alerts from Datadog, Grafana, dbt Cloud, GCP, and Azure into a single JSON schema allows one triage pipeline to deduplicate, enrich, and enforce data-privacy boundaries uniformly:

Contract Field Operational Purpose
event_id, source_tool, received_at Idempotent traceability and duplicate suppression across retries/webhooks.
system / pipeline / data_product Identifies the exact affected asset for catalog & lineage lookup.
severity, symptom, observed_vs_threshold Captures what broke and quantitative magnitude (e.g., freshness lag 82m > 45m SLO).
correlation_id (run_id, job_id, trace_id) Links upstream root causes to downstream cascading alerts deterministically.
owner / routing_key Determines accountable squad and escalation channel.
dashboard_url, runbook_url, run_url One-click verification context for both the investigating agent and on-call humans.
data_classification Governs redaction & whether payload fields may be sent to external LLM endpoints.
  • Alert on symptoms and SLOs, not every low-level cause: Page when “Data Product X will breach its 06:00 freshness SLO” (using multi-window burn-rate alerts where applicable) rather than paging separately on every worker retry underneath.
  • Unify human severity (`P1–P4`) with agent response grades (`G0–G6`): Base severity on business impact—not on which monitoring tool screamed loudest—and align scales (`P1 ≈ G6`, `P2 ≈ G5`, `P3 ≈ G2–G4`, `P4 ≈ G0–G1`).
  • Run periodic alert-actionability audits: Track the percentage of alerts per rule that resulted in a real human or runbook action; tune or delete chronic no-ops.
  • Keep agent briefs scannable in 10 seconds: What happened · Likely consumer impact · Most probable cause + cited evidence · Confidence score · Suggested next step & links.
05 · Pillar 3 — Toil Elimination

Fixing Things With Less Toil: The Four Decisions & Watch State

Each of the four scoped agent decisions carries distinct trigger patterns, required evidence, and starting autonomy ceilings:

Agent Decision Typical Triggers Required Evidence in Payload Starting Autonomy
1. Escalate Ongoing Event Critical pipeline failure, active SLO breach, consumer-visible delay, repeated retries Consumer impact, lineage blast radius, timeline, suspected cause, actions already tried L3 (Notify)
2. Escalate Predicted Failure Runtime creeping upward, warehouse/API quota trending to ceiling, expiring certs/secrets Trend slope, forecast breach window, confidence, cost of acting vs. waiting — explicitly labeled PREDICTION L1 (Advise)
3. Watch More Carefully Single transient blip, sub-threshold warning, ambiguous upstream signal Watch reason, metrics to re-poll, next check timestamp, escalation condition, max TTL L3 (Internal State)
4. Retry / Recover Known transient signature (503, lock timeout, slot contention), matching idempotent runbook Runbook ID, verified preconditions, blast radius, attempt counter, post-action check plan L1 → L2 → L3

The Active Watch State Machine

Binary alerting forces a bad trade-off between paging too early on transient blips or paging too late on slow-burning degradation. Giving the agent a first-class, time-bounded Watch State (`G1`) solves this cleanly:

Candidate Toil Matrix: Where to Automate vs. Where to Hold the Line

Operational Scenario Governed Agent Action Risk Target Level
Transient dbt Cloud failure (timeout, warehouse busy) Retry once from point of failure with backoff LOW L2 → L3
Upstream source feed delayed Enter Watch State, recheck freshness, notify owners if SLA window tightens LOW L3 (Watch)
Non-critical dbt data test warning Open enriched ticket with downstream lineage summary LOW L3 (Notify)
Transient cloud orchestrator activity error (GCP / Azure) Propose runbook-backed single activity rerun MEDIUM L2 (Approve)
Quota, slot, or storage trending toward hard limit Send labeled predictive notice with forecast window to owner MEDIUM L1 (Advise)
Historical partition backfill or data reprocessing Draft execution & cost plan only; human reviews & triggers HIGH L1
Expired credentials, breaking schema drift, IAM errors Escalate immediately with root-cause evidence; never auto-fix HIGH L1
06 · Runtime Architecture

Inside the 6-Stage Intelligent Agentic Workflow

What separates an intelligent reliability workflow from brittle cron-script automation is how it handles cross-system context, uncertainty, and budget limits across six tightly guarded stages:

Stage What Happens Where Intelligence Adds Leverage Deterministic Guardrail
1. Intake Normalizes alerts from dbt, GCP, Grafana, Datadog & Azure; deduplicates into one incident. Groups cascading alerts by shared dependency graph & lineage—collapsing 10 alerts into 1 incident. Idempotency keys, rate limits, strict schema validation.
2. Context Attaches service owner, tier, SLOs, downstream consumers, recent git/dbt deploys & maintenance state. RAG retrieval over runbooks, postmortems, and prior incident resolutions. Read-only, least-privilege metadata & tool scopes.
3. Reason Runs a short hypothesis-and-evidence loop across read-only MCP tools; forecasts SLA risk. Ranks competing causes, runs a self-critique pass, cites tool links, and outputs calibrated confidence. Hard step, latency & token budgets; tool outputs fenced as untrusted data.
4. Grade Computes severity & response grade from G0 to G6. Explains the multi-factor rationale in clear human prose. Base math & policy overrides computed in deterministic code—never by the LLM.
5. Act Executes the grade’s playbook: digest, watch, advise, self-heal, one-click proposal, or page. Selects minimum-blast-radius action and pre-computes rollback steps. Non-AI policy engine, allowlist, resource lock, human gate on G4+.
6. Verify & Learn Checks post-action metrics, re-grades dynamically, and captures operator feedback. Flags noisy rules and drafts candidate runbook/threshold updates from real outcomes. Humans review & merge all policy, runbook, or threshold changes.
Bounded Reasoning Rule (Stage 3) Inside Stage 3, the agent tests ranked hypotheses (e.g., late upstream source vs. schema change vs. BigQuery slot quota vs. expired secret) one read-only tool call at a time. If its step or token budget runs out before reaching high confidence, it stops, grades conservatively, and hands over to a human with the evidence gathered so far—never guessing.
07 · Proportional Response

The Graded Response Model (G0 to G6)

Replacing a blunt page / don’t-page switch with a seven-band response ladder lets the platform respond proportionally to risk. Keep the two orthogonal axes distinct:

  • Situation Grade (`G0–G6`): How serious the incident is and which operational playbook applies.
  • Action Autonomy (`L0–L4`): How much authority a specific runbook has earned. For example, a G3 scenario only self-heals automatically if that exact runbook holds L3 approval; otherwise policy downgrades execution to a G4 one-click proposal.
Grade Situation Playbook Response Control Mode Data Platform Example
G0 RECORD Informational or already self-cleared blip Log to timeline & daily digest; zero chat noise Auto dbt warning that cleared on next scheduled run
G1 WATCH Unusual signal, zero current impact Timed re-polling with explicit exit/escalation criteria Auto (L3 Watch) Freshness lag rising but still comfortably inside SLO
G2 INFORM Predicted future breach or low-impact issue Post forecast, time-to-breach & recommendation in team channel Auto (L1 Advise) Runtime slope predicts nightly batch misses 06:00 SLA
G3 SELF-HEAL Known transient fault + approved L3 runbook Run allowlisted idempotent retry/rerun, verify, then post audit note Auto (L3 Action) Single 503 API blip → retry dbt job once from failure point
G4 PROPOSE Known fix with medium blast radius (backfill, scale-up) Prepare parameterized plan + rollback; request 1-click sign-off Human Approves (L2) Partition backfill after late-arriving upstream file
G5 ESCALATE Active critical SLO breach or high impact w/ low confidence Page on-call with concise synthesis, evidence links & ruled-out causes Human Leads Tier-1 executive revenue feed failed; retry exhausted
G6 MAJOR Multi-system or business-wide outage Open major incident; agent shifts to read-only scribe & status drafter Incident Commander Regional cloud or warehouse outage blocking multiple domains

Try the Deterministic G0–G6 Grading Engine

Start with a transparent formula your team can read and audit: multiply Impact (1–3) × Criticality (1–3) × Urgency (1–3) for a base score (`1–27`), adjust for trend and downstream blast radius, and apply hard policy overrides (low confidence, failed self-heal, critical tier, maintenance windows). 08 · Resilience & Rollout

When the Agent Itself Fails: Guardrails, Fallbacks & Pilot Roadmap

An SRE system must never become a single point of failure—or an amplification vector during an outage. Designing for robustness means explicitly engineering for how the agent itself can fail:

Failure Mode Operational Risk Mandatory Engineering Control
Agent or LLM API Outage Critical alerts silently dropped Independent critical-alert path bypasses the agent directly to PagerDuty; dead-man’s heartbeat on intake & agent forwards raw alerts on timeout.
Cloud Outage Alert Storm Token spike, queue backlog & page flood Back-pressure queue, dependency-graph grouping, rate caps, and automatic Storm Mode opening a single G6 bridge instead of 100 pages.
Duplicate / Replayed Webhooks Double retries or duplicate pages Idempotency keys on both intake events and actions + per-resource mutex locks preventing concurrent mutations.
Retry Amplification Overloading a struggling database or duplicating rows Strictly idempotent runbooks, max-attempt ceilings, exponential backoff with jitter, and per-signature circuit breakers.
Hallucinated Root Cause Misleading on-call or picking wrong runbook Mandatory evidence URLs per claim, critic pass, low-confidence auto-action block, and strict runbook allowlisting.
Prompt Injection in Logs Crafted log text tricking agent into action Fence tool/log payloads as untrusted data; LLM holds zero credentials; non-AI policy engine authorizes every action.
Prompt / Model Drift Silent triage regression after model update Version prompts, models & YAML policies; replay historical incident benchmark suite in CI before shadow promotion.
Runaway Reasoning Loop High latency & unbounded token spend Hard per-incident step, wall-clock, and token budgets; on budget exhaustion, grade conservatively and hand over.

Pragmatic Rollout Roadmap & Success Metrics

Start small on one well-owned, business-relevant pipeline with recurring transient faults, establish baseline metrics first, and earn autonomy one rung at a time:

  1. Phase 1 — Foundation & Coverage Map: Audit blind spots, add missing heartbeats, standardize the 7-field alert contract, and baseline weekly alert volume, duplicate rate, MTTA/MTTR, and out-of-hours pages.
  2. Phase 2 — Shadow Mode (`L0`) & Replay Harness: Run intake, correlation, RAG context, and G0–G6 grading silently alongside humans; measure human-agreement precision and missed/false escalations.
  3. Phase 3 — Enriched Triage (`L1`) & One-Click Proposals (`L2`): Post concise evidence-linked briefs in Slack/Teams and enable one-click human approval cards for vetted retry runbooks.
  4. Phase 4 — Earned Bounded Self-Heal (`L3`): Promote only high-precision, low-blast-radius idempotent runbooks to L3, governed continuously by policy-denial tracking and a 1-click kill switch.
